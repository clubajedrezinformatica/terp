Según Dijkstra debuggear es resolver los errores del código. Verificación y testeo de los programas ayudan a evitar programas. Si la cultura del desarrollo no requiere que los resultados coincidan con los requerimientos previos, seguramente será necesario debuggear. El contexto es que en la ingeniería de software la carencia de errores es una MÉTRICA DE CALIDAD, test de stress, aceptación, integración, regresión y UNIDAD. Se hace hincapié en los TESTS DE UNIDAD. 
Para mitigar los errores se utiliza testing. En backend se quiere probar si en vez de dos o tres o diez peticiones por minuto le llegan cien mil, entonces se pone a prueba el sistema para ver si la base de datos entra en deadlock, o hay un stackoverflow (se supera la capacidad de la memoria disponible), etc. El de aceptación e integración son tests de unidad de más alto nivel cuya semántica cambia según el contexto de uso. El test de aceptación se utiliza cuando recibimos un módulo de terceros y lo revisamos. El de integración permite integrar módulos de terceros. El de regresión se verifica que algo que ya funcionaba continúe funcionando. En el test de unidad permite testear la unidad mínima de ejecución. Un método podría implementar más de una unidad funcional. Testear cada rama condicional sería un test de unidad, testear la función completa sería un test de aceptación o test funcional. Ejemplo de test: cifrado César. 
PARADOJA DE TESTING 
Escribir casos de test es deseable, pero no es gratis, sino costoso. Es importante porque el tiempo gastado escribiendo test cases no es usado para nueva funcionalidad. Si todos los recursos van a test y no a funcionalidad el proyecto fracasa. Pero si no hay test habrá problemas de calidad. Por otra parte no hay que testear todos los métodos. El único caso para este tipo de testeo es una implementación en máquina virtual donde se quiera chequear que la concatenación de string está bien implementado en el compilador. Puede haber un test para chequear el buen funcionamiento de un framework, no es chequeo de la lógica de negocios. Si extendiéramos el framework si se necesitaría un test. Hay estrategias para diseñar test cases: PARTICIONES EQUIVALENTES y CASOS DE BORDE. 
Otro aspecto del testing es cuando se depende de un objeto que todavía no está. Uno podría escribir un programa que trabaje con ese módulo, pero no podemos testearlo. Hay un lenguaje de patrones que permite usar estrategias para resolver este problema. Imaginemos un sistema de ascensores donde no tenemos un motor. La solución es el lenguaje de patrones TEST DOUBLE. A veces no es práctico, puede haber diferentes estrategias (ascensores inteligentes). Se puede jugar con las diferentes estrategias. Es más práctico utilizar este patrón. En general propone crear un objeto que es una maqueta (objeto polimórfico) que reemplace al objeto real que no tenemos (el motor del ascensor). Se parece a un proxy (que representa a un objeto remoto). Son cosas parecidas porque el problema es similar y la técnica para resolverlo es la misma: desacoplar lo que varía, encapsularlo en un objeto y que la clase principal no se entere si está interactuando con el objeto real o su maqueta. Es una simulación. Los rangos de implementación van desde un cascarón vacío (null object pattern, la idea de tener un objeto que sea vacío, aunque en este patrón se modela un concepto de nulidad que viene del dominio). Se pueden ver similitudes. 
TEST STUB: cascarón vacío que es polimórfico pero no hace nada. Sirve para que el test case compile. 
TEST SPY: un stub que tiene un registro de los msjs que recibe. El espía puede devolver si recibió o no mensajes (si tengo que saber si se activaron ciertas funciones se imprime por terminal el flujo de ejecución, en este caso el espía sabe qué mensaje se activaron). 
MOCK OBJECT: no solo registra qué mensajes se activaron sino que registra el orden de activación de los mismos. El stub se comporta como lo que falta pero además verifica la corrección de ese comportamiento. 
FAKE OBJECT: es un mock que se comporta en tiempo real como el objeto que no tenemos. 

A medida que usamos los patrones más complejos la implementación es más difícil. 

El esquema de cascada no es adaptable al cambio, aunque fue la norma hasta la década del 90. Mucho de la ingeniería hasta esos años concebía al cambio como caos. Mucha actividad estaba alrededor de esa metodología, había poco testing y una vida feliz, cosa que rara vez se cumplía porque la realidad cambia, los proyectos son largos y a medida que unos trabaja y aprende de un dominio, las cosas estarán sujetas a cambio. Luego se cambió al paradigma de prototipos que permitiera ampliar la funcionalidad. Hubo autores que hablaron de métodos de desarrollo basados en prototipo: autores japoneses propusieron el Kanban y el Scrum. Es la metodología de prototipos. También estuvo el extreme programming, que fue revolucionario, y un coletazo fue el TDD. Estos son los procesos o métodos ágiles. 
El scrum fue revolucionario porque el testing está en medio del proceso y no al final. Se planea, se diseña, se escriben tests y se programa para validar los tests y continuar con la siguiente fase del proyecto. Es un paradigma incremental de desarrollo. El approach ágil no tiene una división de tareas tan marcado. Los diseñadores pueden testear y viceversa. Todas las personas tiene afinidad a ciertos roles pero no hay jerarquías, el desarrollo es iterativo en incremental, se valora el feedback (dentro del grupo o del cliente final), y lo que varía en entender un dominio hace que se preste atención y se adapte el cambio (change embraced). Entonces la pregunta es si tenemos una rueda de análisis, diseño, codificación y testing, y Beck propone empezar por el testing, primero hay que saber cuál es la funcionalidad de mayor generalidad, lo que se engancha con que los requerimientos se escriben como historias de usuario que se guardan en un backlog, que es desorganizado y tiene varios puntos de vista y criterios: lo que hace el project manager junto al cliente es dar prioridad a esas historias. Al elegir un conjunto de historias no se codea, sino que se escriben los test cases, lo que tiene un impacto: combina el test previo al desarrollo y refactoring: modificaciones al código fuente para que sea más adaptable o lo hace más legible (el código no cambia su comportamiento, sino que se hace más legible o adaptable). El refactoring es importante porque son cambios de código que no modifican su funcionalidad (nunca se rompe lo ya implementado). Las ventajas del testing previo al código: se produce un cambio positivo en que sabiendo lo que hay que testear codear es escribir el código para que pase el test implementado. El concepto de velocity es importante: ayuda a mantener los tiempos ajustados. También el grupo de trabajo se enfoca en escribir código que pasen los test cases. Se acota la producción de código fuente. 
GRANULARIDAD
test de aceptación: cosas que funcionan por separado funcionan al integrarse 
test de unidad 

TDD: es importante escribir los tests primero (test driven -> son lo que guían el desarrollo). Primero se escriben tests generales, y luego se hacen tests de clase + tests de unidad. 
Una vez superados los tests, se refactoriza para asegurar la buena calidad de código. 
El diseño es incremental, los programadores escriben sus propios tests, el diseño debe consistir en componentes altamente cohesivos... se necesitan herramientas para la escritura (JUnit o PyUnit, etc). También se necesitan herramientas para hacer refactoring (automático o semiautomático). Resumiendo el TDD es que dada su manera de trabajo reduce el sobrediseño, proceso de elicitación del dominio, la arquitectura surge incrementalmente, el refactoring mantiene código mínimo y limpio, cada requerimiento se convierte en un test case, el último release es un "entregable", y permite una alta adaptabilidad al cambio. Algunos problemas son que hay que mantener un objetivo a largo plazo, los cambios en una base de datos pueden se costosos, y debe haber interacción permanente con los expertos del dominio (o los clientes del negocio). Los cambios son gratuitos si son internos al sistema, no si se involucran recursos externos.
